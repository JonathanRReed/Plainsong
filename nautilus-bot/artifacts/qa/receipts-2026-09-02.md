# Receipts the ledger lacked (2026-09-02/03)

Parity program item B12.2. The lane's brief asked for seven measurements the
parity ledger was missing, on the condition that every one of them be taken on
a quiet machine — 1-minute load average below about 6 on this 14-core Mac.

**Four were taken; the rest were not.** The machine never reached the load
threshold — it hovered between 27 and 279 for four hours and had fallen only to
about 10-14 by the time this was written — and the ASR latency runs were then
blocked outright by a macOS keychain prompt. What follows is what was captured,
at what load, what was not, and exactly why, so the next run starts from
evidence rather than from a second guess.

## Environment

- Hardware: Apple M4 Pro, 14 logical CPUs, 24 GB (25 769 803 776 bytes).
- OS: macOS 27.0 (build 26A5406e).
- Toolchain: rustc 1.93.0 (254b59607 2026-01-19).
- Source: `parity-waves` at `cd3c80c4` plus the lane B12 commits; the packaged
  build below was made at `a84d2abb`.
- Sidecar feature set: the shipped one, `scripts/sidecar-cargo-features.mjs`
  → `--features candle-metal`.
- Fixtures: `scripts/fixtures/local-quality-gate.wav` (5.32 s) and
  `scripts/fixtures/real-speech-44s.wav` (43.97 s) — the same pair the August
  latency receipt and the September 1 acceleration receipt used.

### Machine state, which is the finding

The 1-minute load average was sampled every 90 s from 20:24 on 2026-09-02 to
02:19 on 2026-09-03 while other parity lanes ran `cargo build`, `cargo test`
and `electron-builder`. Observed range: **9.3 to 279** on 14 cores, and it did
not fall below 25 until 02:19. At 00:45 `vm_stat` reported roughly 90 MB of
free memory.

The brief's condition was a 1-minute load below about 6. That never happened.
The three numbers below were taken at load 10-14, which is why each one states
its load and why the two that are load-sensitive say so. The September 1
acceleration receipt records what happens when latency is measured under real
contention — a Distil-Whisper process that got paged out returned numbers 70×
worse than the same binary minutes earlier — so nothing timing-shaped was
forced through here.

## Captured

### Cold start

| Metric | Value |
| --- | --- |
| Command | `node scripts/cold-start-gate.mjs --threshold-ms 2500 --ready-output-pattern "App rendered" --electron-logging --isolate-plainsong-data -- release/mac-arm64/Plainsong.app/Contents/MacOS/Plainsong` |
| Launch to "App rendered" | **728 ms** |
| Threshold | 2 500 ms |
| Result | **pass**, exit 0 |
| load1 at start | **10.16** (above the brief's ceiling of ~6) |

Isolated `PLAINSONG_DATA_DIR`, `PLAINSONG_CONFIG_DIR` and Electron profile, so
the operator's own data was untouched and the model directory was empty.

At load 10 this is a pessimistic reading, not an optimistic one — contention
can only make a launch slower — so the 3.4× headroom under the threshold is a
safe conclusion even though the load was above the ceiling. Re-take it quietly
before quoting 728 ms as the number.

Note for whoever runs this next: `bun run gate:cold-start` exits 1 even on a
pass, because the packaged app writes Electron teardown noise
(`Render frame was disposed before WebFrameMain could be accessed`,
`Network service crashed or was terminated`) to stderr as it is stopped.
Invoking `node scripts/cold-start-gate.mjs` directly with the same arguments
exits 0 and prints `"ok": true`. That is worth fixing before this gate is
trusted in CI.

### Idle sidecar resident memory

| Metric | Value |
| --- | --- |
| Binary | `release/mac-arm64/Plainsong.app/Contents/Resources/sidecar/plainsong-sidecar` |
| State | idle after `[sidecar] ready`, empty data dir, stdin held open |
| RSS | **26 624 KB = 26.0 MiB**, identical across 10 one-second samples |
| CPU | **0.0%** across all 10 samples |
| load1 | 13.89 at start, 12.66 at end |

**This contradicts the ledger.** `docs/competitive-positioning.md` says "1.9 MB
idle RSS on the sidecar". The measured figure is roughly 14× that. RSS is far
less load-sensitive than latency — it is a page count, not a stopwatch — so
the order of magnitude here is trustworthy even at load 13. The old number
should not be repeated.

What this does *not* cover: RSS during a transcription (Parakeet on the 44 s
fixture, Distil on Metal) was blocked with the latency runs, see below.

### Idle CPU with the call-detection poll on versus off

60 samples each, one second apart, after a 30 s warmup, over the packaged app's
whole process tree. Receipts: `artifacts/qa/macos/idle-cpu-call-detection-on.md`
and `…-off.md`.

| Setting | Average | p95 | Peak | Threshold | Result | load1 at start |
| --- | --- | --- | --- | --- | --- | --- |
| Call detection **on** | **0.07%** | 0.20% | 2.70% | ≤ 1% average | pass | 11.97 |
| Call detection **off** | **0.10%** | 0.00% | 5.00% | ≤ 1% average | pass | 14.35 |

**The poll costs nothing measurable.** Both runs are an order of magnitude under
the 1% ceiling, and the *off* run averaged marginally higher than the *on* run —
which is only possible if the difference between them is below the noise floor
of a machine at load 12-14. The poll interval does not need tuning.

Read that as "no detectable cost", not as "detection is free": a clean
separation would need both runs on a genuinely idle machine, and neither was.
What it does rule out is the failure the brief was worried about — a poll busy
enough to show up in an idle-CPU baseline.

Both runs used an isolated profile whose `models/` directory was pre-created
empty. That is deliberate and worth knowing for the re-run: it keeps the app off
the keychain-backed integrity-receipt path that blocked the ASR benchmarks in
the same session, and call detection needs no model either way.

### `bun run electron:pack` cannot produce an unsigned build

The brief asked for an unsigned pack. It does not complete:

```
⨯ Packaged native helper verification failed:
  plainsong CLI has no readable entitlement property list
    at readEntitlements (scripts/verify-packaged-native-helpers.mjs:177:5)
    at requireEmptyEntitlements (scripts/verify-packaged-native-helpers.mjs:211:24)
    at Packager.emitAfterPack (app-builder-lib/src/packager.ts:338:5)
```

`electron-builder.yml` sets `hardenedRuntime: true` and `notarize: true`, and
the `afterPack` hook reads each bundled helper's entitlements with
`codesign -d --entitlements`. With `CSC_IDENTITY_AUTO_DISCOVERY=false` — the
way to pack without a signing prompt — electron-builder never signs, so there
is no entitlements plist for the hook to read and the build fails.

The `.app` is still complete when the hook runs, because `afterPack` fires
after the bundle is written. It is ad-hoc linker-signed
(`codesign -dv` → `Signature=adhoc`, `Identifier=Electron`,
`Sealed Resources=none`), carries the correct `com.plainsong.app` identifier
and `0.9.0-beta.3` version, and contains the sidecar, the CLI, and all three
native helpers. That is the bundle `gate:size` measured.

Consequence for the brief's item 4: `bun run gate:packaged:macos:native` is
this same script, so it fails for the same reason on an unsigned pack. It does
not tolerate unsigned, and no receipt for it is claimed here.

Nothing was clicked. No signing identity was requested and no keychain prompt
appeared at any point (`pgrep SecurityAgent` was empty before and after).

### Support bundle, written by the packaged sidecar

Not one of the seven, but it is the evidence behind item B12.1 and it needed no
quiet machine. The packaged `plainsong-sidecar` was driven over its own stdio
JSON-RPC with an empty `PLAINSONG_DATA_DIR`:

- `describe_support_bundle` returned the 9-section list, 5 redaction rules and
  8 exclusions the Settings screen shows.
- `write_support_bundle_privileged` wrote a 5 805-byte zip holding 9 files.
- A relative `targetPath` was refused:
  `targetPath must be an absolute path, got 'relative/path.zip'`.

The log lines handed in were deliberately hostile. Redacted output:

```
[sidecar] ... INFO plainsong_lib::download: staged [redacted:path]
[main] WARN invite mail queued for [redacted:email]
[sidecar] WARN plainsong_lib::llm: provider rejected [redacted:key]
[sidecar] INFO plainsong_lib::asr: [redacted: this line mentioned captured text]
[main] LOG [shortcuts] registered dictation shortcut
```

The first line is what caught a real bug: on the first run it came out as
`[redacted:path] Support/Plainsong/models/base.bin`, because the pattern
stopped at the space in "Application Support" and left the file name behind.
Fixed in `a84d2abb`; the line above is the output after the fix.

## Not captured, and why

The ASR latency runs were stopped by a **macOS keychain prompt**, not by load.
At 02:20, with the load down to 10, `benchmark-latency` (release build, shipped
feature set, sha256 `974ac43f…02eb`) was pointed at an isolated data dir with
the real model directories symlinked in. It printed its banner and then sat at
**0.0% CPU and 7.4 MB RSS for 20 minutes**, while `pgrep SecurityAgent` showed
a live prompt. This is exactly the blocker
`artifacts/qa/acceleration-receipt-2026-09-01.md` describes: the model-integrity
receipts are HMAC'd with a key in the login keychain
(`download::model_integrity_mac_key` → `secrets::get_internal_secret`), and a
freshly built ad-hoc-signed binary reading that item blocks on the "wants to use
your confidential information" dialog until a human clicks.

**Nothing was clicked.** The benchmark process was killed and the prompt was
left for the machine's owner.

Hypothesis remains the Metal shader cache; unproven, and the keychain wait is now a second candidate explanation for the Sep 1 figures worth ruling out. |

Everything in that table except the two `dictation_timing.rs` rows needs one
thing to become measurable by an unattended run: a sidecar binary whose
signature the login keychain already trusts, or a documented way for the
integrity path to fail closed instead of blocking when the keychain will not
answer without a human. Load was not the obstacle in the end.

## What the next run needs

Everything above except the two `dictation_timing.rs` items is a re-run away.
The pieces are staged and do not need rebuilding:

- `release/mac-arm64/Plainsong.app` (ad-hoc signed, at `a84d2abb`).
- A `benchmark-latency` built with the shipped feature set, sha256
  `974ac43fd0bc4eaba7a0c9e5b0bb63ea6aaa31d6cc02bf9f590717f5194902eb`.
- An isolated `PLAINSONG_DATA_DIR` with `whisper`, `parakeet`,
  `distil_whisper`, `qwen3_asr` and `bundled_cleanup` symlinked in.

The two scripts that drive the whole set are kept with the session scratchpad
rather than committed, because they hardcode this machine's paths.

Two things cannot come from a re-run of a script:

1. The real stop-to-insert latency. That needs somebody at the Mac: hold the
   dictation shortcut, speak, release, and read the `DictationTimingRecord` the
   sidecar logs.
2. Any ASR latency or in-flight RSS number, until the keychain prompt is dealt
   with. A person can clear it by running the binary once and clicking "Always
   Allow"; an unattended agent cannot, and should not.
